# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

"Mois D Zois" — an English-language Discord bot (discord.py 2.x, slash commands) for channel watching, RSS feeds (e.g. YouTube/news), and music playback (yt-dlp + FFmpeg). All commands live under a single `/mois` group, gated by a hashed, pepper-keyed authorization check (`@Auth.instance().user`, see "Hashed auth" below) rather than a plaintext ID whitelist. There is no bot-side moderation layer — Discord's native roles/permissions cover that.

## Running

```
pip install -e .
python main.py
```

Dependencies live in `pyproject.toml`'s `[project.dependencies]` (with `[build-system]`/`[tool.setuptools]` making it installable) — there is no separate `requirements.txt` to keep in sync; `pip install -e .` is the one source of truth for both "what does this need" and "how do I set up a dev environment."

No test framework or linter is configured; modules are smoke-tested ad hoc with inline Python.

## Architecture

Everything is a class (owner mandate: OOP with `__init__`/DI everywhere). `main.py` only builds `Settings` and `MoisBot` and runs it.

C4-component layout:

- `orchestrator/` — bot orchestration only (renamed from `core/`: everything in here wires services, routes, and gateway events together — "core" didn't say that, "orchestrator" does): `bot.py` (`MoisBot(commands.Bot)`: constructs and owns all services as attributes — `db`, `embeds`, `log`, `transfer`, `watcher`, `http`, `auth`, `rss`, `music`, `tickets`, `voice_channels`, `router` — plus `self.events`, a dict built at the end of `__init__` mapping event name → private handler method (`_on_ready`, `_on_message`, `_on_message_delete`, `_on_message_edit`, `_on_reaction_add`, `_on_command_completion`, `_on_voice_state_update`). Every discord.py-required gateway method (`on_ready`, `on_message`, `on_message_delete`, `on_message_edit`, `on_raw_reaction_add`, `on_voice_state_update`, `on_app_command_completion`) is, without exception, a one-line `await self.handle_event("name", **kwargs)` — `on_ready` used to do its tree-sync work inline instead of dispatching, which was the one gap in an otherwise uniform pattern; moving that into `_on_ready` closed it, so there's now exactly one shape for "a gateway event happened" across the whole class, not one shape plus one exception. `handle_event(name, **kwargs)` (bottom-most public entry point) looks the name up in `self.events` and calls it — same dict-dispatch shape as `Music.handle`/`Router.dispatch`, adapted for the fact that Discord's gateway events don't share one signature. `_on_message_delete`/`_on_message_edit` share their "should this even be logged" guard via a small `_should_log(author, guild)` staticmethod rather than repeating `not author.bot and guild is not None` twice. `setup_hook`/`close` (service lifecycle: `db.init()`, cog/dynamic-item registration, each service's `start()`/`stop()`) and `_on_command_error` (assigned directly to `self.tree.on_error`, a discord.py app_commands-specific callback) deliberately do **not** go through `self.events` — they're not "a gateway event happened, dispatch it" in the same sense, and forcing them through the same dict would be the "blanket rule regardless of fit" this pattern explicitly warns against (see "Service internals" below). Likewise, the six-plus thin `on_*` wrapper methods themselves stay as explicit, individually-named methods rather than being generated in a loop (`setattr(self, f"on_{name}", ...)`) — discord.py's dispatcher finds handlers by literal attribute name, so metaprogramming them away would still need the same names to exist somewhere, just less readably; the same "framework needs the real names" reasoning already applied to `slash_commands/commands.py`'s command stubs), `router.py` (`Router`: plain dict `self.handlers` name → coroutine; `bot.router.get(name)`, `dispatch(...)`), `handlers.py` (`Handlers`: command logic; registers each method in the router dict on construction), `registry.py` (`ServiceRegistry`/`registry` singleton — pure decorator-based bookkeeping of which services exist, see "Service registry" below), `embeds.py` (`Embeds` — moved in from the former top-level `helpers/`, which existed for this one file alone; instantiated once on the bot), `voice.py` (`Voice` — the bot's hardcoded personality lines, keyed by outcome name (`"ticket_duplicate"`, `"music_playing"`, ...) and filled in via `str.format`; instantiated once on the bot exactly like `Embeds`, injected into `Tickets`/`Music` as `chat`. Deliberately not tied to any specific real person's actual speech — see `config/llm/persona.md` for the voice/register this follows and the rule against that. This is the interim, hardcoded version of what `config/llm/` is scaffolded for eventually turning into an LLM-driven persona; `Voice` is expected to be replaced or wrapped, not extended forever).
- `slash_commands/` — `commands.py` (`CommandsCog`: slash-command stubs only, nested under a single `app_commands.Group` named `mois` (with a `music` subgroup); signatures exist because discord.py derives parameters from them; every body is a one-line `router.dispatch`. This directory used to be called `cogs/` (discord.py's own term for this layer, a "Cog") — renamed because the term is opaque outside discord.py itself; what it holds hasn't changed, it's still exactly the framework-required command-registration layer, kept separate from `orchestrator/` (bot orchestration) and `services/` (business logic) for that reason) and `helper/` (a package, not a single file, per the "one class per file" convention — `mois_group.py`, `delegating_group.py`, `music_group.py`, `role_gate.py`, each holding one `app_commands.Group` subclass or, for `RoleGate`, the shared role-check logic those subclasses call into; `helper/__init__.py` re-exports all four. These access-control classes don't live in `commands.py` since `commands.py` is specifically the framework-mandated command-stub layer, and access control mixed into that file would read like two unrelated concerns bolted together). discord.py's `Command._check_can_run` only consults a command's *immediate* parent group's `interaction_check`, it does not walk the full ancestor chain — so every subgroup nested under `mois` MUST define its own `interaction_check` (never a bare `app_commands.Group`, which inherits discord.py's default `interaction_check` that unconditionally returns `True`; this was a real, exploited-in-review bug: the `music` subgroup was completely unauthenticated for one session). **Two valid subgroup patterns exist, both explicit — the only forbidden one is neither:** `DelegatingGroup` forwards its check verbatim to `self.parent.interaction_check(interaction)`, for a subgroup that should require the exact same privilege as `mois` itself (not currently used by anything, kept as the ready-to-use pattern for a future admin-only subgroup). `MusicGroup` (used by `music`) is the other pattern — a subgroup with its **own**, deliberately *different and less restrictive* check, since music playback isn't the same privilege tier as `logchannel`/`export`: it checks the caller's roles against `config.yaml`'s `music.allowed_role_ids` via `RoleGate.check(interaction, "music", "allowed_role_ids")`, fails closed (an empty/unconfigured list denies everyone, same shape as `auth.json`'s empty `users`/`roles`), and is not gated by `@Auth.instance().user` or the pepper/hash system at all — deliberately, since forcing music access through the same hashed-admin allowlist as ticket/log-channel management would mean granting full bot admin just to play a song. **Any future subgroup nested under `mois` (or under another subgroup) MUST explicitly write one of these two shapes — inherit the parent's check via `DelegatingGroup`, or define its own real check — never a bare `app_commands.Group`, or its commands silently skip auth entirely.**

A third situation exists at the `mois` level itself, not a subgroup: `MoisGroup.interaction_check` gates `mois`'s own *direct* children, and as of `/mois idle`/`/mois troll` (community-tier, deliberately flat — not `/mois music idle` — despite living right next to `logchannel`/`export`) those direct children are no longer all one privilege tier. Since discord.py hands `interaction_check` the `interaction` (which carries `interaction.command.name`), `MoisGroup.interaction_check` branches on that name: `role_gated_commands = {"idle", "troll"}` routes to `RoleGate.check(interaction, "music", "allowed_role_ids")` (the exact same check `MusicGroup` uses — shared, not duplicated), everything else (`logchannel`, `export`, and any future admin-tier direct child) routes to `_admin_check`, the `@Auth.instance().user`-decorated method that used to be `interaction_check` itself (the decorator's policy lookup uses the function's own name, so `auth.json`'s `functions` key is `_admin_check`, not `interaction_check`, since the rename). **Any future direct child of `mois` needs an explicit decision here too: either its name joins `role_gated_commands`, or it falls through to `_admin_check` by default — there is no third, unguarded path, same "never accidentally inherit the wrong check" rule as the subgroup case above.** A third branch was later added deliberately, not as an exception to this rule but as its logical extension: `open_commands = {"birthday"}` returns `True` outright, no `RoleGate`, no `Auth` — `/mois birthday` only ever reads/writes the calling user's own row in the `birthdays` table, so there is nothing to gate beyond what Discord itself already gates (who can see `/mois` at all). The rule stands unchanged: every direct child still needs one explicit, named decision among exactly three now-known branches — `open_commands`, `role_gated_commands`, or the `_admin_check` fallthrough — never an implicit fourth path.
- `services/` groups every service under one more directory level by use case, not just by name — `services/<group>/<name>/`, not the flat `services/<name>/` this section otherwise writes for brevity: `announcements/` (`rss`, `free_games`, `twitch_watch`, `birthdays`, `webhooks` — everything whose job is "something happened → post it to a Discord channel," whether that something arrives by polling a feed/store/stream, on a schedule, or as an inbound webhook), `media_requests/` (`tickets`, `imdb`, `watchlist_export` — the ticket-driven movie-recommendation pipeline: a ticket comes in, gets IMDb-matched, and the matched collection can be pushed out), `channel_logging/` (`channel_watch`, `message_log`, `transfer`, `backfill` — observing and persisting Discord channel activity), `voice/` (`music`, `voice_channels`, `troll` — anything that joins or manages a voice channel). `admin_api/` stays a direct child of `services/`, ungrouped — it's the dashboard's own backend, not a business-logic "use case" alongside the others, and forcing a single-member parent folder around it would add a directory for no reader benefit. Grouping is purely a directory-level concern: `ServiceRegistry` route strings (`"/rss"`, `"/webhooks"`, ...) don't encode the group and didn't change, nor did any class name, `__init__.py` re-export shape, or the getter/setter/one-class-per-file rules below — every rule in this section applies identically inside a group as it did at the old flat level. The one place group membership becomes a real dependency is a cross-group import: `voice/troll/core.py` reaches into `voice/music/helper` and `voice/voice_channels/util` (`from services.voice.music.helper import Player`) — still fine, since `troll`, `music`, and `voice_channels` all landed in the same `voice/` group precisely because they're voice-channel features that lean on each other; a future cross-*group* import (e.g. something in `announcements/` reaching into `media_requests/`) is the signal to stop and ask whether the two "use cases" were actually the same one, not to reach for a `sys.path` hack. Each of the four group folders (`announcements/`, `media_requests/`, `channel_logging/`, `voice/`) is itself an empty, otherwise-unremarkable Python package — a bare `__init__.py` with nothing to re-export, since nothing imports from the group name itself, only from `services.<group>.<name>`.
- `services/<name>/` — self-contained components, package `__init__.py` re-exports the class from `core.py` (one line, nothing else). Layout inside each service package (see "Service internals" below): `message_log/` (`Log`), `transfer/` (`Transfer`), `channel_watch/` (`Watcher` — arbitrary list of watched channels from `config.yaml` `watch.channels`, writes structured rows via `WatcherRepository`; channels flagged `tickets: true` are instead handled entirely by `Tickets`), `rss/` (`Rss` — polls feed URLs from `config.yaml` `rss.feeds` on a `discord.ext.tasks` loop, dedupes via `RssRepository`, posts to the configured channel per feed; parsing lives in `rss/util.py`'s `FeedParser`, constructed once as `self.feed_parser` in `Rss.__init__`), `music/` (`Music(bot, chat)` — dict-dispatch over `play`/`skip`/`pause`/`resume`/`stop`/`queue`, delegates queue/voice state to `Player` and yt-dlp resolution to `SongResolver`, both in `music/helper.py`; playback starts at `Player.default_volume` (0.2, i.e. 20%, not the FFmpeg-source default of 100%) via `discord.PCMVolumeTransformer` wrapping the `FFmpegPCMAudio` source — plain `FFmpegPCMAudio` has no adjustable volume, the transformer is what makes `voice_client.source.volume` live-settable — and the "now playing" message carries a `VolumeView` (two buttons, ±10%, clamped to `[0.0, 2.0]`) that adjusts `voice_client.source.volume` directly plus persists the new level in `Player.volumes` so the *next* track picks it up too. `Player.advance` also pushes the track title onto the voice channel's status (`VoiceChannel.edit(status=...)`, discord.py ≥2.4) — but `advance` runs inside `discord.py`'s `AudioPlayer` thread (a real `threading.Thread`, not the asyncio loop — confirmed by reading `discord.player.AudioPlayer.__init__`/`_call_after`) when called from the `after=` callback on track completion, so the status update is scheduled via `asyncio.run_coroutine_threadsafe(..., self.bot.loop)` rather than awaited directly; this is why `Player` takes `bot` in its constructor now. Only members holding a role from `config.yaml`'s `music.allowed_role_ids` can reach any `/mois music` command at all — see the `MusicGroup` entry above — and since `Music._ensure_voice` always joins *the calling user's own* voice channel, that role list is also the answer to "who can make the bot join a channel." `SongResolver.resolve` runs `link` through two independent checks before it ever reaches yt-dlp, since it's unauthenticated-adjacent user input and yt-dlp's generic extractor will otherwise happily fetch any host/scheme it's given — `music/util.py`'s `MusicLinkResolver` (constructed once as `self.link_resolver` in `SongResolver.__init__`), whose `resolve` method first restricts input to an allowlist of exact YouTube hostnames (`youtube.com`, `www.youtube.com`, `m.youtube.com`, `music.youtube.com`, `youtu.be`; a scheme-less string that still looks like a bare YouTube URL is rejected outright rather than silently treated as a search term, since typing `youtube.com/watch?v=...` without `https://` is the realistic accident here), extracts *only* the video ID via `urlparse`/`parse_qs` (never trusting the surrounding string — the whole point, since `youtube.com.evil.com` or `evil.com/youtube.com/...` would pass a naive substring check), rejects a `?v=` query with more than one value, and rebuilds a clean canonical `https://www.youtube.com/watch?v=<id>` itself rather than forwarding anything attacker-supplied; non-URL-shaped text (no scheme, doesn't look like a bare YouTube link) passes through unchanged as a search term, since yt-dlp's `default_search: "ytsearch"` already handles that. `MusicLinkResolver.is_safe` (scheme + global-IP check via `socket.getaddrinfo`) still runs afterward on the rebuilt/passthrough result — technically redundant against `youtube.com` itself today, kept anyway as a second, differently-failing layer (string-based host allowlist vs. DNS-resolution-based IP check) against the DNS-rebinding class of bug, not because either check alone is insufficient for the current allowlist), `tickets/` (`Tickets` — reaction-driven ticket workflow for `watch.channels` entries with `tickets: true`: status open/operation/closed/archive/currently_not_possible via emoji reactions configured in `config.yaml` `tickets.emojis` — values are parsed once via `discord.PartialEmoji.from_str`, matched back by `emoji.id` for custom emojis or the unicode string itself, never by name — duplicate-content detection via `tickets/util.py`'s `ContentHasher` (constructed once as `self.content_hasher` in `Tickets.__init__`), TTL-based closed→archive, and a due-timestamp-driven DM reminder loop for `currently_not_possible` using a persistent `discord.ui.DynamicItem` button, `TicketBlockedButton` in `tickets/helper.py` (a standalone class, like `music/helper.py`'s `Player`/`SongResolver` — nesting it inside `Tickets` was tried and reverted: it read as two classes pretending to be one, and `discord.ui.DynamicItem`'s own construction machinery (`__init_subclass__` consuming `template=`, `from_custom_id` building instances with no `Tickets` reference in scope) doesn't compose with inheriting from `Tickets` either), so it survives restarts; the actual status mutation lives in the `@Auth.instance().user`-decorated `_apply_status`, kept separate from `handle_reaction` so the auth check only fires for real ticket reactions, not every reaction anywhere on the server. The reminder recipient (`ReminderUserId`) lives in gitignored `config/config.ini`, not committed `config.yaml` — it's a real Discord user ID, and every other identity in this codebase is pepper-hashed, so a plaintext ID has no business in a committed file. `Tickets._verified_reminder_user_id` additionally cross-checks it against `auth.json`'s hashed `users` list at construction; a mismatch (or auth being disabled) zeroes it out and logs one `CRITICAL` line instead of silently DMing a stale or misconfigured ID — same fail-closed-not-fail-crash shape as `Auth` itself), `voice_channels/` (`VoiceChannels(bot, settings)` — keeps exactly one empty "overflow" voice channel available per configured category (`config.yaml`'s `voice_channels.categories`, each with a `category_id`, `max_generic_channels` cap, and an ordered `name_pool`), autonomously creating/deleting channels as people join/leave. **Channel ownership is derived from the channel's current name every time, never stored** — `voice_channels/util.py`'s `SlotNaming` (constructed once as `self.slot_naming` in `VoiceChannels.__init__`; `slot_from_name`/`name_for_slot` are `@staticmethod`s on it since neither needs instance state) is the only place that decides whether a channel is bot-managed, by checking whether its live name matches something the pool would generate (bare pool name first, e.g. `"Mois"`, then `"Mois 2"`, `"Mois 3"`, ... once the pool is exhausted). This is the load-bearing safety property for a service that autonomously deletes Discord channels: nothing is ever touched based on a remembered ID, only on what the name currently says, so a fixed/real channel is never at risk (its name will never match), and a user renaming a bot-created channel away instantly and permanently removes it from the bot's consideration — no code path un-does that. `_reconcile_category` additionally hard-excludes `guild.afk_channel` even though the naming check should already exclude it (belt-and-suspenders, cheap to keep). Reconciliation runs on `on_voice_state_update` (a new gateway event, requires the `voice_states` intent — not privileged, no Developer Portal toggle needed) — `handle_voice_state_update`, `@log`-decorated as its own entry point since it's a genuinely separate trigger from the loop, not a shared internal — and, self-healing-style like `Tickets.check_archive`, on a periodic `check_interval_seconds` loop (`check`, also its own `@log`) in case an event is ever missed; both funnel into the same `_reconcile_all`/`_reconcile_locked`/`_reconcile_category` chain, guarded by a per-`(guild_id, category_id)` `asyncio.Lock` so two near-simultaneous voice-state events can't race each other into over-creating. **Per-user creation throttle**: each category's `max_creations_per_user` (default 2) caps how many channel creations one Discord user can trigger within one `check_interval_seconds` window (`VoiceChannels.creation_times`, an in-memory `(category_id, user_id) → [timestamps]` map, pruned to the rolling window on read — no DB needed for a throttle this short-lived, same reasoning as `Auth.last_call_at`'s cooldown) — this defends against one user rapidly join/leave-thrashing a spare channel to force repeated create/delete API churn, which the `max_generic_channels` cap alone doesn't prevent (that only bounds the *total* count, not the *rate* of churn). Only live, voice-state-triggered creations are throttled (`triggering_user_id` is the joining/leaving member's ID); the periodic safety-net loop passes `triggering_user_id=None` and is exempt, since it has no attributable user and already only runs once per `check_interval_seconds` regardless.

no API key needed, so it's the one of these five with nothing to fail closed on beyond an unset channel), `twitch_watch/` (`TwitchWatch` — `util.py`'s `TwitchAuth` owns the Helix OAuth client-credentials flow and token caching; same fail-closed-on-missing-config shape as `TwitchWatch`, triggered on demand by the admin-gated `/mois export_movies` rather than its own loop, since there's no natural "poll" cadence for "did the collection change" the way there is for an external feed). `dependencies/http.py::Http` gained `post_json` plus an optional `headers=` on every method for these two OAuth/Bearer-token consumers — `get_text`/`get_json`'s existing callers (`Rss`, `Imdb`) are unaffected since `headers` defaults to `None`.

No discord import; injected via constructors (`Auth.instance()`/`ServiceRegistry.instance()` are the one deliberate exception — see below).

Command chain: stub in `slash_commands/` → route name in `Handlers.__init__` routes tuple → handler method → service.

`slash_commands/` and `orchestrator/` stay separate directories rather than folding into `services/` (considered and rejected): `slash_commands/` is discord.py's mandatory framework-registration layer, `orchestrator/` is bot orchestration (wiring services together, dispatching gateway events), and `services/` is swappable business logic — collapsing them would lose a real, useful boundary for one that's only nominally simpler (fewer top-level folders, same amount of code doing different jobs). `dependencies/` stays reserved for shared connections only (DB, HTTP, settings, auth) — it does not grow to hold orchestration code just because both are "not a service." The former top-level `helpers/` was folded into `orchestrator/` (it held exactly one file, `embeds.py`, so a whole separate directory for it wasn't earning its keep) — `dependencies/` and `helpers/` as a pairing is gone; the durable split is `dependencies/` (connections) vs. `orchestrator/` (wiring) vs. `services/` (business logic).

### Service internals: core/helper/util

Every `services/<name>/` package holds its main class in `core.py` (what `__init__.py` re-exports) — that file follows the usual "`__init__` then helpers then the bottom-most public entry point" layout. Only add `helper.py` (service-specific supporting classes) and/or `util.py` (pure, stateless supporting classes — see below) when there is actual content to move there — do not create empty placeholder files. Every service that touches the database has a Repository class (`LogRepository`, `TransferRepository`, `WatcherRepository`, `RssRepository`, `TicketRepository` — see "Getters read, setters write" below) living under `helper.py`/`helper/`.

**One class per file, always — no exceptions for "just two small classes."** The moment a `helper.py`/`util.py`/any other supporting file would need to hold a second class, it stops being a file and becomes a same-named **package**: delete `helper.py`, create `helper/` in its place, give each class its own file named after it in snake_case, and have `helper/__init__.py` re-export whatever the rest of the codebase needs from outside the package (mirroring the existing "`__init__.py` re-exports the class, one line" habit, just with one `from ... import X` line per class instead of exactly one). External call sites never notice or need to change — `from services.tickets.helper import TicketBlockedButton` resolves identically whether `helper` is a module or a package, since Python treats both the same way for import purposes. Current examples of this: `music/helper/` (`player.py` → `Player`, `song_resolver.py` → `SongResolver`, `volume_view.py` → `VolumeView`), `tickets/helper/` (`ticket_repository.py` → `TicketRepository`, `ticket_blocked_button.py` → `TicketBlockedButton`), `slash_commands/helper/` (`mois_group.py`, `delegating_group.py`, `music_group.py`), `dependencies/auth/policy/` (`auth_function_policy.py`, `auth_policy.py` — nested two levels deep, since `dependencies/auth/` was already a package and `policy.py` inside it grew a second class), `dependencies/logger/` (`core.py` → `Logging`, `log.py` → the `log` descriptor class — `core.py` rather than `logging.py` for the same "main class of the package" reason `dependencies/auth/core.py` isn't named `auth.py`, and specifically *not* `logging.py` here, which would sit one import-path segment away from shadowing the stdlib `logging` module `core.py` itself needs to `import`). Do not nest a supporting class inside its owning service class (`Tickets.TicketBlockedButton`) either — tried and reverted, reads as two classes pretending to be one; it goes in its own file under `helper/` instead.

**No free functions, no bare module-level constants — everything lives in a class, including `util.py`.** This is an owner mandate, not a style suggestion: `rss/util.py`'s `FeedParser` (constant `self.atom_ns` set in `__init__`, methods `_text`/`_parse_atom_entry`/`_parse_rss_item`/`parse_feed`), `tickets/util.py`'s `ContentHasher` (one `@staticmethod`, `hash`), `music/util.py`'s `MusicLinkResolver` (constants `self.youtube_hosts`/`self.bare_youtube_pattern`/etc. in `__init__`, `is_safe`/`resolve` plus private helpers), and `voice_channels/util.py`'s `SlotNaming` (three `@staticmethod`s, no instance state needed) are all `util.py` classes, constructed once in their owning service's `__init__` and stored as `self.<name>` (`self.feed_parser`, `self.content_hasher`, `self.link_resolver`, `self.slot_naming`) exactly like `helper/`'s Repository classes — a `util.py` class with no meaningful state just means most/all of its methods end up `@staticmethod`, which is fine and still gets instantiated and called the same way (`self.slot_naming.name_for_slot(...)`) for consistency across the codebase. None of the current `util.py` files have grown a second class yet, but the moment one does, it follows the same file → package split described above (a `util/` folder, not a multi-class `util.py`).

When a service's public surface is naturally a set of "/command" cases (like `Music`), prefer a dict dispatch in `__init__` (`self.actions = {"play": self._play, ...}`) with one public `handle(action, ...)` at the bottom doing the lookup — mirrors the existing `Router` pattern in `orchestrator/router.py`. This same shape is used outside `services/` too: `MoisBot.events`/`handle_event` in `orchestrator/bot.py` dict-dispatches gateway events, and `Handlers.music_routes` in `orchestrator/handlers.py` maps each `music_*` route name to a `Music` action string, registering `functools.partial(self._music, action)` for each instead of six near-identical one-line methods — the discord.py-mandated command stubs in `slash_commands/commands.py` stay explicit (the framework needs the real signatures), but everything downstream of them can go through one adapter. Services whose multiple public methods are each triggered by a genuinely different Discord event (e.g. `Tickets.handle_message` vs `Tickets.handle_reaction`, or `Rss`'s loop-runner vs `Log`'s delete/edit hooks) keep one method per event instead of forcing them through a single dispatcher — dict-dispatch is for cases sharing one call shape, not a blanket rule to apply regardless of fit.

### The `@log` decorator

`dependencies/logger.py`'s `log` is a descriptor class (not a plain function) so it works as `@log` on both sync and async methods; it times the call and logs `"... took ...s"`, plus logs+re-raises exceptions. Apply it to exactly the method(s) a bot event handler or a `discord.ext.tasks` loop actually calls directly — not to shared internals (`Log.log_delete`/`log_edit` get it, `log_embed` doesn't; `Rss.poll`/`Tickets.check_archive`/`Tickets.check_reminders` get it, their private `_poll_feed`/loop bodies don't). By the same rule, every `start()`/`stop()` across the three `tasks.loop`-based services (`Rss`, `Tickets`, `VoiceChannels`) is `@log`-decorated too — `MoisBot.setup_hook`/`close` call all three directly, so they qualify exactly like any other directly-called method.

**Do not decorate a method that is passed directly to `tasks.loop(...)`.** The `@log` descriptor turns `self.method` into a `functools.partial`, and `tasks.loop()` type-checks its argument as a coroutine function at bind time — decorating that method breaks bot startup. Pattern used in `Rss`/`Tickets`: `tasks.loop(...)(self._run_x_loop)` binds a thin, undecorated pass-through that just calls the real, `@log`-decorated public method (`poll`, `check_archive`, `check_reminders`). `dependencies/auth/core.py`'s `@Auth.instance().user` sidesteps this hazard entirely by being a plain function decorator (not a descriptor) — none of the current `@Auth.instance().user` targets are loop-bound, but if one ever is, apply the same thin-pass-through pattern rather than decorating the loop-bound method directly.

**Decorator ordering**: if a method ever needs both `@log` and `@Auth.instance().user`, `@Auth.instance().user` goes outermost (written above `@log`) so a denial short-circuits before the timing/logging of the actual work runs.

### Hashed auth (`@Auth.instance().user`)

`dependencies/auth/core.py` gates the handful of privileged functions (`MoisGroup.interaction_check`, `Tickets._apply_status`, `Handlers.logchannel`, `Handlers.export`) without ever storing or logging a real Discord user ID. The real protection is a secret pepper, not code obscurity — the design has to hold up even if a teammate reads it. `Auth.user` itself stays thin decorator plumbing (timing, logging, dispatch to `func`); the actual decision lives in two extracted methods — `_requires_auth(name)` (policy lookup) and `_authorize(args)` (identity extraction + `is_authorized` + rate limit) — kept separate so the authorization logic is a reusable, independently-testable piece rather than buried in the closure:

- **Pepper**: `[BotConfig] AuthPepper` in `config/config.ini` (gitignored, same file as the bot token), with an env-var fallback (`ZOIS_AUTH_PEPPER`) that exists only so tests/tooling can set one without touching the real file. User IDs are compared via `HMAC-SHA256(pepper, id)`, never a bare hash — a bare hash of a Discord snowflake is brute-forceable from a guild's member list alone, since the IDs aren't secret, only their pepper-keyed digest is.
- **Policy file**: `config/auth.json` (committed — safe to commit because the hashed IDs in it are meaningless without the pepper) holds `functions` (name → `auth_required`, defaults to `true`/fail-closed if a decorated function's name is missing from the file), `users` (hashed IDs), `roles` (plain role IDs — role membership is already visible in the guild, hashing it would hide nothing). Validated on load against `dependencies/auth/policy.py`'s `AuthFunctionPolicy`/`AuthPolicy` pydantic models (`extra="forbid"`) — that's robustness against a broken edit of a trusted local file, not injection defense — there is no untrusted input path into this file. These models live in their own file, separate from `Auth`'s actual behavior in `core.py`, since "validate this JSON's shape" and "make the authorization decision" are different concerns that happen to be small enough to have shared one file before `dependencies/auth.py` grew into the `dependencies/auth/` package.
- **Fail-closed, not fail-crash**: a missing pepper or unreadable/invalid `auth.json` does not raise at import time (that would take down RSS/tickets/logging too, which have nothing to do with auth) — it sets `Auth.enabled = False`, logs one English `CRITICAL` line at construction, and every check denies from then on. Empty `users`/`roles` in `auth.json` is also a hard deny for everyone, including the owner, until populated — see README for the self-enrollment command.
- **Never log the identifier**: `@Auth.instance().user` logs only `"auth check for <name>: granted|denied (<duration>s)"` in English — never the user ID or its hash. A hash in logs is still a stable pseudonym that lets a reader correlate everything one person does, which defeats the whole point of hashing in the first place.
- **Singleton by necessity, via a `@classmethod instance()` accessor, not a bare module variable**: `Auth` and `ServiceRegistry` both carry a class attribute `_instance = None` and a `@classmethod instance(cls)` (`if cls._instance is None: cls._instance = cls(); return cls._instance`) — a textbook OOP Singleton, not a `name = ClassName()` line sitting naked at module scope. Placed near the bottom of each class, right before the class's true main public entry (`Auth.user`, `ServiceRegistry.route`) — Python fully builds a class (every method it contains) before any other module can call into it, so `instance()`'s position within the class body is purely a readability choice, not a functional constraint; it reads best sitting right next to the method it exists to support. Every call site (`@Auth.instance().user` in `slash_commands/helper.py`/`orchestrator/handlers.py`/`services/media_requests/tickets/core.py`, `self.auth = Auth.instance()` in `orchestrator/bot.py`, `@ServiceRegistry.instance().route("/name")` in every service's `core.py`, `ServiceRegistry.instance().summary` in `main.py`) calls the classmethod fresh; all of them resolve to the exact same object, verified via `is` in the smoke test. A shared instance is still required here, for the same reason a bare module variable was: `@Auth.instance().user` decorates `MoisGroup.interaction_check` in `slash_commands/helper.py`'s class body, which evaluates at import time — `orchestrator/bot.py` imports `slash_commands.commands`, which imports `slash_commands.helper`, and that happens before `MoisBot(settings)` is ever constructed, so no `__init__` has run yet that could hand out a fresh instance. `Auth.instance()`'s first call (triggered by that very decorator) is what lazily constructs the one shared `Auth`, exactly as `auth = Auth()` used to at module-body execution — the difference is that the cached reference and its constructor now live inside the class (`Auth._instance`, `Auth.instance()`) rather than as a bare name floating at module scope, which is what "no free functions, everything in a class" actually asks for here. The same reasoning applies to `ServiceRegistry`: if each service's `@ServiceRegistry.instance().route(...)` somehow returned a different object per call, every service would record its route into a separate, immediately-orphaned instance, and `ServiceRegistry.instance().summary` in `main.py` would have nothing to read — the classmethod's caching is precisely what prevents that. Do not "fix" this by moving construction into `MoisBot.__init__`, and do not replace `self.auth = Auth.instance()` with a bare `Auth()` call, which would silently create a second, independent copy of in-memory state (e.g. `Auth.last_call_at`) that should be one.
- **Per-user cooldown**: `auth.json`'s `cooldown_seconds` (default `2.0`) throttles each *already-authorized* hashed user to one `@Auth.instance().user` call per window, tracked in-memory (`Auth.last_call_at`, keyed by hashed ID, never the raw ID). This is deliberately not a "client+server combined" scheme — a Discord bot has no trusted client half to combine with (the Discord client isn't our code), so there's no second party to hold a secret. It's a plain anti-spam cooldown, nothing more. A rate-limited call gets a distinct denial message ("please wait a moment") from a genuinely unauthorized one ("no permission"); that distinction is safe to expose because it only ever reaches someone who already passed the authorization check.

### Log language

Everything is English — log messages (`dependencies/logger.py`'s `Logging.get_logger`/`log`/`Auth`), user-facing Discord text (embeds, `interaction.response.send_message(...)`, DMs, command/parameter names), and internal exception text. This used to be split (German user-facing text, English logs); that split was dropped so the whole codebase and product surface is one language.

### Service registry

`orchestrator/registry.py`'s `ServiceRegistry` is a plain in-process bookkeeping decorator, not a web server: `@ServiceRegistry.instance().route("/name")` on a service class in `core.py` just records it against the one shared instance (see "Singleton by necessity" above). `main.py` logs `ServiceRegistry.instance().summary` (a `@property`, no parens — it takes no arguments) once at startup so it's visible which services are wired up. A real HTTP layer (health checks, actual `/service` endpoints) is still future work — don't build it ahead of need; the Docker image itself (see "Docker" below) doesn't depend on it existing.

### Docker

`config/deploy/Dockerfile` (`python:3.11-slim` + `ffmpeg` via `apt-get`, `pip install .` — non-editable; editable installs are for local dev via `pip install -e .`, not baked into an immutable image) builds the whole app except `config/` itself, which is declared a `VOLUME` and always supplied at container-run time, never baked into the image — this keeps one image generic across deployments/environments instead of tying it to one owner's token/pepper/policy. `config/deploy/` groups the build tooling (`Dockerfile`, `build_image.sh`, `build_image.ps1`) separately from the actual config data files sitting directly under `config/` (`config.ini`, `config.yaml`, `auth.json`) — deploy tooling isn't itself configuration, but it's not a service either, so it earns its own subfolder rather than cluttering `config/`'s root or getting a whole new top-level directory for three files. Living two directories deep from repo root doesn't change how it's invoked: the build **context** is still the repo root (`COPY pyproject.toml`, `COPY services services`, etc. resolve from there), only the Dockerfile's own location moved — `docker build` needs `-f config/deploy/Dockerfile` to find it, which is exactly what `config/deploy/build_image.sh`/`config/deploy/build_image.ps1` already pass. `.dockerignore` excludes `config/` (and `.git/`, caches) from that build context as a second layer of the "never baked in" guarantee, independent of whichever `COPY` lines the Dockerfile happens to have — note this also means `config/deploy/Dockerfile` itself never ends up inside its own build context, which is fine since nothing `COPY`s from `config/`. `config/deploy/build_image.sh`/`config/deploy/build_image.ps1` are the only sanctioned way to build the image (`cd` two levels up to the repo root, then `docker build -f config/deploy/Dockerfile -t mois-d-zois .`) — scripted rather than ad hoc so the build command itself can't silently drift between machines/people. Running the image needs `-v <host config dir>:/app/config` pointing at a real, populated `config/` (same contents as the non-Docker setup in the README).

That single-container path still works, but the intended way to run the whole thing (bot + `frontend/` dashboard + monitoring) together — deliberately built for a host that runs more than just this one project, e.g. a Raspberry Pi picking up unrelated services over time — is `config/deploy/docker-compose.yml` — living next to the existing `Dockerfile`/`build_image.*` since it's deploy tooling, not config data, same distinction this section already draws above; the one piece of compose-related *data*, `config/.env` (the `ADMIN_API_KEY` Compose needs), sits directly under `config/` next to `config.ini`/`auth.json` instead — driven by pnpm (`pnpm dc:up`/`dc:down`/`dc:logs`/`dc:ps`/`dc:restart` in the root `package.json`, each already pointing at `-f config/deploy/docker-compose.yml --env-file config/.env` so they're safe to run from the repo root with no extra flags; plain wrappers around `docker compose ...`, no actual Node dependency needed since it's only a task-runner here — `dc:down` adds `--remove-orphans` for a clean teardown but never touches the named `kuma-data` volume, so Uptime Kuma's history survives a down/up cycle). `frontend/` is a pnpm workspace member (`pnpm-workspace.yaml`) — it moved off `npm`/`package-lock.json` for this, specifically so one package manager runs both the compose tooling and the frontend's own scripts. The compose stack's `bot`/`frontend` services all sit behind a `traefik:v3` container on an **external** `edge` Docker network (`docker network create edge`, created once, outside Compose's own lifecycle) rather than Compose's default network — external and named on purpose, so a completely separate, future compose stack on the same host can join the same network and get routed by the same Traefik without this repo's `docker-compose.yml` ever being touched. Traefik only routes containers carrying `traefik.enable=true` (`--providers.docker.exposedbydefault=false`) — a fail-closed default matching the rest of this codebase's posture, not "expose everything unless told not to." `frontend/Dockerfile`'s build **context is the repo root**, not `frontend/` — Next.js's `output: "standalone"` traces the whole pnpm workspace (needs `pnpm-workspace.yaml`/the root `pnpm-lock.yaml` visible, and nests its build output under `.next/standalone/frontend/` accordingly) since `frontend/` is a workspace member, not a standalone package; copying only `frontend/` as the build context breaks that tracing. `uptime-kuma` is the one service in the stack **not** behind Traefik — published directly on its own port instead, since Kuma's own docs don't support being served from a Traefik subpath reliably, and fighting that isn't worth it for a monitoring dashboard nobody else links to. It's wired back into `services/announcements/webhooks/` (this repo's own webhook relay, see the services list above) via its built-in Webhook notification type hitting the `uptime_kuma` source type — so the monitoring tool this repo depends on to know its own health reports through the exact same relay it's monitoring, not a separate notification path. TLS stays out of this compose stack too, same "deferred, not bolted on ad hoc" reasoning already used elsewhere for this codebase's encryption posture — Traefik listens on port 80 only.

## Code style (owner-mandated, strictly enforced)

- NO docstrings and NO comments anywhere. Readability comes from structure and names instead.
- No free functions and no bare module-level constants, anywhere, including `util.py` files — everything lives inside a class, even a class whose methods all end up `@staticmethod` because there's no instance state. See "Service internals: core/helper/util" above for the concrete examples (`FeedParser`, `ContentHasher`, `MusicLinkResolver`, `SlotNaming`) and why module-level singletons (`auth`, `registry`) are the sole, narrowly-scoped exception, not a loophole.
- Class layout: `__init__` first with ALL constants/config values enumerated as `self` attributes; then private/deep methods in the order they are used (the gnarly detail functions at the deepest level); the main public entry function sits at the BOTTOM of the class so you can read top-down how the service works through its steps. For the three `tasks.loop`-based services (`Rss`, `Tickets`, `VoiceChannels`), `start()`/`stop()` sit at the very bottom, after the "work" methods (`poll`/`check_archive`+`check_reminders`/`check`+`handle_voice_state_update`) — an observed, consistent sub-convention across all three, not just one of them, worth following for any future `tasks.loop`-based service. Classes with no single "how you use this" entry point (`Database`, `Embeds`, the Repository classes, `Player`) are exempt from the bottom-entry-point framing — they're data/utility facades with several coequal public methods by design, not services with one call shape.
- Getters read, setters write: DB access goes through `get_*`/`set_*`/`add_*` methods **only** on a per-service Repository class (`LogRepository`, `TransferRepository`, `WatcherRepository`, `RssRepository`, `TicketRepository` — each in its service's `helper.py`), never on bare `Database`. No other verbs — a repository method that isn't a clean read/write/create gets folded into one of the three rather than growing a fourth prefix (`find_*`, `upsert_*`, `remove_*`, `mark_*`, `reset_*` all existed at one point and were consolidated back down): `TicketRepository.get_ticket_by_hash` (was `find_ticket_by_hash` — a lookup is a `get_*`, full stop), `RssRepository.get_seen` (was `has_seen`, returned `bool` — now returns the row or `None`, matching every other `get_*` in the codebase, so the caller does the `is not None` check instead of the repository doing it), `TicketRepository.set_ticket_blocked(ticket_id, next_check_at)` (was three separate methods — `upsert_ticket_blocked`, `remove_ticket_blocked`, `reset_ticket_reminder` — collapsed into one `set_*`: passing a real timestamp upserts the row, passing `None` deletes it; every call site now reads as "set the blocked state to X or clear it" instead of three differently-named operations doing overlapping things), `TicketRepository.set_reminder_pending` (was `mark_reminder_sent`). `Database` (`dependencies/database.py`) only holds the shared connection primitives (`connect()`, `now()`) and the centralized `init()` with every `CREATE TABLE` — the whole DB's shape stays visible in one place, while each service only sees the queries relevant to it. `MoisBot.__init__` wires this by constructing one `Database` and wrapping it once per service: `Log(LogRepository(self.db), ...)`, `Tickets(TicketRepository(self.db), self, settings)`, etc. — every service still just calls `self.db.get_x(...)`/`self.db.add_x(...)` on whatever repository it was handed, unaware it's not talking to `Database` directly; this is also the seam for swapping SQLite for something else later without touching service code. Passing whole objects through a chain (e.g. `bot.tickets.db`) is fine. Config values are read once via `Settings.get(...)` into `self` attributes in `__init__` — there is no setter for YAML-sourced values, only for actual runtime state (a repository's `set_*`).
- Simple imports, simple names (`Log`, `Watcher`, `Handlers`, `Embeds` — no fancy naming). No decorative emojis in code, comments, or bot text; the status emojis used as message reactions in `tickets/` are a configured feature (`config.yaml` `tickets.emojis`), not an exception to this rule. Minimal type annotations; only `slash_commands/` signatures need them (discord.py requirement).
- English for all user-facing strings and everything else — see "Log language" below.
- Getters/setters: use `@property`/`@x.setter` only for genuinely argument-less accessors (`Settings.token`, `ServiceRegistry.summary`). Anything parameterized (all of `Database`'s `get_*`/`set_*`/`add_*`, `Log.get_channel(guild)`, etc.) stays a plain method — Python properties cannot take arguments, and mixing conventions within one class (e.g. `Database`) would be worse than picking one and keeping it. This is a narrowing of the getter/setter rule below, not a replacement for it.
- Keep code slim, incremental, lint-clean; no dead code, no duplication.
- File paths are constructed once, in `__init__`, as named `self` attributes (`self.db_path`, `self.config_path`, `self.yaml_path`, ...) — never built inline inside a method body (`open(self.base_dir / "whatever")` buried three calls deep). Same reasoning as the config-values rule above: compute it once where the class's shape is declared, reference the name everywhere else.
- Walrus (`:=`) is used narrowly: only to collapse a "fetch a value, then immediately check it for `None`/truthiness" pair into the `if` line itself (e.g. `if (ticket := self.db.get_ticket_by_message(...)) is None: return`) — this is a well-established, easy-to-read Python idiom. Do not chain multiple walrus assignments inside one boolean expression (`if (a := ...) and (b := ...):`) or nest comprehensions more than one level deep — both trade a few lines for a condition the reader has to unpack all at once, which works against the "readability comes from structure" rule above.

## Config & runtime

- All config lives in `config/` (kept out of repo root so root only holds actual code/package directories, not a scatter of loose files): `config/config.ini` holds the bot token, `AuthPepper`, and `ReminderUserId` (all gitignored, never commit or print — `ReminderUserId` is a real Discord user ID, so it lives with the other secrets, not in the committed yaml). `config/config.yaml` holds all non-identity tunables (export dir, watched channels, ticket status emojis/TTLs, RSS feeds/poll interval) and is gitignored since it carries real server IDs; `config/config.example.yaml` is the committed, sanitized template. `config/auth.json` holds the auth policy — hashed user IDs, plain role IDs, cooldown seconds, and the function → auth-required map — and is gitignored too (published repo); `config/auth.example.json` is the committed template with empty `users`/`roles`. `ReminderUserId` must additionally hash to an entry in `auth.json`'s `users` list (checked once at `Tickets.__init__` via `Tickets._verified_reminder_user_id`) — a raw ID that doesn't correspond to an authorized hash gets zeroed out (reminders silently disabled) plus one `CRITICAL` log line, rather than DMing whatever ID happens to be sitting in the ini file. `Settings`/`Auth` both resolve these paths via `self.config_dir = self.base_dir / "config"` in their own `__init__`. `Settings.get(*path, default=...)` reads `config.yaml` only — there used to be a second, `Settings.defaults` dict duplicating every value already in `config.yaml` (down to the literal ticket emoji strings and interval numbers), which is exactly the kind of drift risk it looks like: change a value in `config.yaml` and the Python-side copy silently goes stale. Removed. Every consumer already passes its own `default=` to `settings.get(...)` at the call site (`Rss.__init__`'s `settings.get("rss", "poll_seconds", default=900)`, `Tickets.__init__`'s `settings.get("tickets", "archive_after_days", default=3)`, etc.) — that inline default is now the *only* fallback, living right next to the code that actually uses the value instead of in a second, disconnected dict. New `config.yaml` tunables need a `default=` on their own `settings.get(...)` call, not an entry anywhere else.
- FFmpeg must be installed separately on the host machine for music playback (not a pip package).
- `bot.db` (SQLite) lives under `config/` too (`config/bot.db`) — stashed with the rest of config for the same declutter-root reasoning, even though it's runtime data rather than configuration; still gitignored (the bare `bot.db` pattern in `.gitignore` matches at any depth, verified via `git check-ignore -v config/bot.db`). `message_log.txt`, `exports/`, `__pycache__` stay at repo root, also gitignored — `message_log.txt` specifically is a leftover from an earlier, pre-refactor version of this codebase that wrote message-delete logs to a flat file (real Discord IDs/usernames in plaintext); nothing in the current code writes it anymore (`Log`'s data lives in `bot.db`/Discord embeds instead), but an old copy with real data can still exist on a dev machine from before the refactor — stays gitignored for that reason even though it's otherwise dead weight, never delete this `.gitignore` line on the assumption "nothing writes it" without first checking whether a stale copy with real data is sitting on disk. `*.egg-info/` (a setuptools-generated build-metadata directory, created even by `pip install --dry-run -e .`) is gitignored too — it's a disposable artifact of the packaging metadata step, not something that needs to exist between runs; safe to delete any time it shows up.
- Requires privileged intents in the Discord Developer Portal: Message Content and Server Members. `voice_states` (needed for `VoiceChannels`/`on_voice_state_update`) is also enabled in `_build_intents` but is not privileged — no Developer Portal toggle needed for it.
- `config/llm/persona.md` is documentation, not code (no `__init__.py`, not an importable package) — it describes the bot's voice for whoever eventually builds the LLM-backed persona `Voice` is standing in for. The actual `Voice` class lives in `orchestrator/voice.py`, not under `config/`, even though it's conceptually related — `config/` holds data (yaml/json/ini/docs), not code that `services/` imports from; putting importable Python there would have business logic depending on the config directory, backwards from every other dependency in this codebase.
